# run linkw wave 3 (lane w3-a): THE SHADOW TEMPLATES.
#
# The two shadow template BMDs are static .data in this overlay, and until now
# every byte of them was a HOLE. That is worth stating precisely, because the
# port did not read garbage here -- it read ZEROS, and for a different reason
# than three separate source comments claimed.
#
# --pack pads the space between two named symbols with a ZEROED gap array, and
# data_ov001_020ad470 (8 bytes) and data_ov001_020ad628 are both on the line
# above. So 0x020ad478..0x020ad628 -- 432 bytes holding BOTH templates, both
# their bones and both their materials -- was emitted as one zero-filled pad.
# That is the "the real body parses a zero stub" that hal/actor_class_faces.cpp
# and hal/cxxname_bridge.cpp describe: not absent bytes, PRESENT ZERO bytes.
#
# THE CUBOID CHAIN IS LIVE. src/_ZN11ShadowModel10InitCuboidEv.cpp is seated
# this wave and its body is SetFile(&data_020ad524, 1, -1), so every symbol
# below is storage the matched code genuinely reaches. Each was found by
# following relocs.txt out of the template, not by taking a span, and each is
# sized by its own next-symbol delta (config/arm9/overlays/ov001/symbols.txt).
# Verified against the raw image (extracted/overlays/overlay_0001.bin, 12800
# bytes = base 0x020aa420 .. .data end 0x020ad620, which is the whole file --
# the yaml's code_size 8032 is the COMPRESSED length and sizes nothing here):
#
#   data_ov001_020ad524  0x3c  the cuboid BMD_File. numBones 1, numMaterials 1,
#                              numTextures 0, numPalettes 0 -- a flat untextured
#                              quad, which is what a drop shadow is.
#     +0x08 -> 0x020ad59c        bones      data_ov001_020ad59c  0x40
#     +0x10 -> 0x020ab618        unk_10     data_ov001_020ab618  0x08
#     +0x28 -> 0x020ad4f4        materials  data_ov001_020ad4f4  0x30
#     +0x2c -> 0x020ad644        unk_2c     data_ov001_020ad644  bss, 4
#   the bone at 0x020ad59c reaches three more:
#     +0x04 -> 0x020ad4a8        data_ov001_020ad4a8  0x0c
#     +0x34 -> 0x020ab5fc        materialIds  data_ov001_020ab5fc  0x04
#     +0x38 -> 0x020ab5f8        data_ov001_020ab5f8  0x04
#   the material at 0x020ad4f4 reaches one more:
#     +0x00 -> 0x020ad49c        data_ov001_020ad49c  0x0c   (shared with the
#                                cylinder material -- listed once)
#
# The material's flags word at +0x24 reads 0x001f0080 in the ROM, which is the
# record func_02046120 rewrites (0x30 stride, &= 0xc0ffff0f, opacity into
# bits 16..20). The bytes and the code agree, which is the check that the
# addresses above are the shadow's and not a neighbour's.
#
# WHY THE 0x020ab5f8 SYMBOLS ARE NAMED RATHER THAN LEFT TO THE GAP PASS.
# delinks.txt puts .text at 0x020aa420..0x020ab5f8 and .data at 0x020ab800, so

# pass would have covered them as port_ov001_gap_* blocks. Named is better:
# make_covering prefers a named symbol over a gap block, and a named symbol is
# sized by its own delta instead of the gap pass's max(t+0x18, next).

#
# Stage::RenderBouncingArrows draws from an OamAttr list at 0x020abd88, which
# is past the 0x020ab800..0x020abb00 run at the top of this file. config names
# it -- config/arm9/overlays/ov001/symbols.txt:111 reads
#
#     _ZN3OAM14BOUNCING_ARROWE kind:data(any) addr:0x020abd88 ambiguous
#
# -- the same `ambiguous` shape as the five HUD tables, and for the same
# reason: ov000 and ov001 share base 0x020aa420, so dsd could not attribute
# the address, and config/arm9/overlays/ov000/symbols.txt:282 carries the
# ov000 misattribution as data_ov000_020abd88. That is lane w3-c's finding and
# it re-checks: this is a PORT change, not a config change.
#
# THE EXTENT IS 16 BYTES AND THE ROM AGREES WITH CONFIG ABOUT IT. That is the
# part worth checking rather than assuming, because OAM::Render is handed this
# pointer and WALKS it -- a short mount is the unbounded-walk failure the
# cross-mount pointer pass in port/CMakeLists.txt describes. Read out of
# extracted/overlays/overlay_0001.bin (base 0x020aa420, 12800 bytes):
#
#   OamAttr is { u32 a01; u16 a2; u16 a3; }, 8 bytes, and OAM::Render returns
#   on a3 == 0xffff after handling that entry.
#     0x020abd88  a01=41f800f4 a2=1080 a3=0000
#     0x020abd90  a01=01f84004 a2=10a2 a3=ffff   <- terminator
#   so the list is exactly two entries and ends at 0x020abd98, which is where
#   the next config symbol starts. The next-symbol delta this mount is sized
#   by and the ROM's own terminator land on the same byte.
#
# 0x020abd98 is NOT taken with it: it reads 020abf20 / 020abdd8 / 020ac078 /
# 020abda8, a pointer table into this overlay and a different object.
#
# NOT YET REFERENCED, and read this before assuming it is live. The matched
# body src/_ZN5Stage20RenderBouncingArrowsEv.cpp spells the template
# func_020abd88 and is not on any slice walk_window reads; the port's own
# stand-in in hal/sub_actors.cpp defines the same C symbol today. Seating the
# matched body needs that stub deleted and the func_020abd88 alternatename
# added beside it, both in hal/sub_actors.cpp, which is not this lane's file.
# The measurement and the handoff are in port/slice_w1l5.txt under LANE w4-e.

#
# Stage::PS_Render draws the pause screen's control-scheme caption from five
# POINTER TABLES, one per system language, each indexed by the control mode in
# data_0209f2dc:
#
#   GetOwnerLanguage() 5 -> func_020abd98   4 -> func_020ac218
#                      3 -> func_020ac64c   2 -> func_020acb68
#                   else -> func_020ad04c
#
# and one more sprite, func_020abac0, for the empty small star. All six are the
# ov000/ov001 shared-base misattribution this file's header describes: dsd
# could not attribute the address, config carries both spellings, and the ov001
# one is the OamAttr data. Two of the six config names are the readable ones --
# 0x020abac0 is _ZN3OAM16SMALL_STAR_EMPTYE (already mounted at the top of this
# file, so it needs no new row) and 0x020ad04c is
# _ZN3OAM21CONTROLLER_MODE_TEXTSE, whose three entries config names
# STANDARD_MODE_TEXT / TOUCH_MODE_TEXT / DUAL_HAND_MODE_TEXT. That naming is
# the check that these five tables are one object per language and not five
# unrelated things.
#
# THE TARGETS ARE MOUNTED WITH THE TABLES, and that is the whole point of the
# rows below. Until now every byte from 0x020abd98 to 0x020ad470 was inside
# pk001_gap_020abd98[5848] -- the --pack ZERO pad this file's wave-3 block
# describes. OAM::Render is handed one of these list pointers and WALKS it to
# the 0xffff terminator, so a table of pointers into zero pad is the unbounded
# walk port/CMakeLists.txt's cross-pass note describes. Mounting the five
# tables alone would not fix that: it would give real pointers into DS main RAM
# instead. So each table's targets are named too, all sixteen of them.
#
# EVERY EXTENT IS CHECKED AGAINST THE ROM, not assumed. OamAttr is
# { u32 a01; u16 a2; u16 a3; } and the list ends after a3 == 0xffff. Walking
# each of the sixteen out of extracted/overlays/overlay_0001.bin (base
# 0x020aa420, 12800 bytes), the terminator lands exactly on the next config
# symbol in all sixteen cases -- 0x020abf20 is 0x158 by next-symbol delta and
# 0x158 by terminator (43 entries), 0x020ad2d0 is 0x180 both ways (48), and so
# on. Same result the w4-e BOUNCING_ARROW block reports for its two entries,
# sixteen more times. So every row below is sized by its plain next-symbol
# delta with no `:0x..` override, and no walk runs off its array.
#
# All twenty-one are IMAGE-BACKED: ov001's .data runs 0x020ab800..0x020ad620
# (config/arm9/overlays/ov001/delinks.txt) and its bss is the 64 bytes
# 0x020ad620..0x020ad660 (overlays.yaml id 1: base_address 34251808 =
# 0x020aa420, ram_size 12800, bss_size 64). Every address here is below
# 0x020ad620, so each mounts real bytes at file offset addr - 0x020aa420.
